= Git Whiteboard App -- User Manual

The Git Whiteboard App is a tool for quickly visualizing various features of the Git version control system. This comes in handy when you want to explain Git's features, for instance, when you're teaching Git to other people. The app allows you to demonstrate the dynamics of a Git graph which is a cumbersome task when you have to use traditional visualization tools such as whiteboards or flip charts.

The app is always initialized with one repository named `my-repo`, the default `main` branch, and one initial commit. You can rename the repository and start adding commits and branches on top of that.

The app's control panel is subdivided into six tabs: `General`, `Commits`, `Refs`, `Merge/Rebase`, `Remote`, and `About`. Select one of these tabs to access the app's functionality.

You can hide the control panel to get more screen space for the Git graph. To do that, click on the chevron icon in the upper right corner of the control panel. The same button is used to make the panel visible again.

== Working With the Git Graph

The Git graph shown in the main area of the app can be moved and zoomed. To move the graph around, left click and hold anywhere in the main area, then drag the graph around. To zoom the graph, press `Ctrl` and zoom in and out with your mouse wheel.

When you want to start from scratch with a new Git graph, you can discard your current graph and get a new one by clicking `Clear graph` on the `General` tab.

== Working With Repositories

The app starts with one repository named `my-repo`. The active repository is shown in the control panel and highlighted on the canvas. Commands from the control panel always apply to the active repository.

You can rename the active repository on the `General` tab by editing the `Repository name` field and clicking `Rename`. The repository label on the canvas and the active repository indicator are updated immediately. Repository names must not be empty, and two visible repositories cannot use the same name.

To add another repository, click `Add Repository` on the `General` tab and enter a unique name. The app supports up to three repositories on the shared canvas. Click a repository region on the canvas to make that repository active.

To share the current session, click `Share`. The app encodes the complete canvas state, including all repositories and their names, in the URL fragment and copies the URL to the clipboard. Opening such a URL restores the saved repositories and graph state, including the positions of the repository regions on the canvas (and thereby the layout of clones below their origin).

== Working With Commits

As with Git itself, the Git Whiteboard App's Git graph is constructed by adding commits as children of the current HEAD commit. To add a new commit, click the `Add commit` button on the `Commits` tab. A new commit will then be added on top of the commit which is currently referenced by the HEAD pointer. Since the app is a demonstration tool, it is not possible to define the contents of a commit or its message.

The app automatically generates a commit id for each new commit. This id is kept very simple but is still unique across all repositories on the canvas (see <<commit-ids>>) so that it is easy to refer to each commit when explaining the graph.

Every branch in the Git graph has its own unique color. When a new commit is added to a branch, the new commit will be colored in that branch's color. Commits created in detached HEAD state are red.

=== Commit Ids [[commit-ids]]

A commit id consists of the first letter of the branch the commit is created on, followed by a number taken from one counter that is shared by all branches (and all repositories, see <<remote-repositories>>). The counter is increased by one for every new commit, no matter which branch it is added to. For example, if the first three commits are made on `main`, they get the ids `m1`, `m2` and `m3`. If you then create a branch `feature` and add a commit, its id is `f4`, not `f1`, because the counter continues across branches.

If currently no branch is checked out (detached HEAD state), the letter `H` is used, e.g. the next commit made in detached HEAD state after `m3` gets the id `H4`.

Because the counter is shared by all repositories on the canvas, a commit that is cloned, pushed, or fetched keeps its id, so the same id in two repositories always denotes the same commit.

In order to keep commit ids recognizable, it is not allowed to create more than one branch with the same first letter. For example, it is not possible to create both a branch `feature_1` and `feature_2`. However, if you're using the namespace notation in your branch names, the namespace part of a branch name is ignored when calculating commit ids. For example, it is allowed to have two branches `feature/foo` and `feature/bar`. Commits on `feature/foo` will then be named e.g. `f4` and `f6` while commits on `feature/bar` get ids such as `b5` and `b7`, drawn from the same shared counter.

=== Amend Commits

To simulate amending commits, click button `Amend commit` on the `Commits` tab. This will create a new commit that replaces the current HEAD commit. The new commit's id is derived from the amended commit by adding an asterisk to the old commit id, e.g. amending commit `f3` will yield a new commit `f3*`.

The old commit is still available as a lost commit (see <<lost_commits,below>> for more about lost commits).

=== Conflicting Changes

The app has no files, so a conflict is demonstrated with a marker: a commit marked as `Conflicting change` touches the one shared imaginary spot. To mark a new commit, tick the checkbox `Conflicting change` on the `Commits` tab before clicking `Add commit` or `Amend commit`. To mark or unmark an existing commit, enter its id in the section `Toggle conflict marker` and click the icon button. A marked commit shows an orange `!` badge. The marker is kept when the graph is shared, cloned, pushed, fetched, cherry-picked or rebased. See ADR 0006 for the background.

=== Cherry-pick Commits

To cherry-pick a commit, enter the id of the commit to be cherry-picked in the text field on the section `Cherry-pick commit` on the `Commits` tab and click the icon button on the text field. This will add a new commit to the current branch with the same color as the cherry-picked commit. The new commit gets a regular id with the cherry-picked commit's id appended in parentheses. For example, if you cherry-pick commit `f2` onto the `main` branch as the fourth commit, the new commit gets the id `m4(f2)`.

=== Check Out Individual Commits

You can check out individual commits, thereby creating a detached HEAD. To do so, you can either double-click on the commit to be checked out, or enter the target commit id in the text field on the section `Check out` on the `Commits` tab and click the icon button on the text field.

== Working With a Detached HEAD: Lost Commits and the Reflog [[lost_commits]]

The Git Whiteboard App allows you to simulate a detached HEAD state. This can be achieved by either checking out an individual commit or a tag. Commits created in this state will be colored in red. Their ids get the `H` prefix for HEAD.

Some Git operations will result in commits being lost in the reflog (e.g., `amend`, `reset`, `rebase`, etc.). This means that such commits do still exist, but are not visible in the Git graph anymore. They can be restored through the reflog. The Git Whiteboard App can show these lost commits as greyed out commit objects. To hide these lost commits, click the checkbox `Show lost commits` on the `General` tab. If this checkbox is deselected, lost commits are not shown. This corresponds to the normal view of a Git history where commits lost in the reflog are not visible in the history.

You can simulate a garbage collection run by clicking the button `Run garbage collection` on the `General` tab. This will delete all commits which are currently lost in the reflog.

== Working with Refs (Branches and Tags)

On the `Refs` tab, you can add, delete, and check out branches and tags, using the sections `Add branch`, `Delete branch`, `Add tag`, and `Delete tag` as well as the check-out sections described below. To check out a branch or tag, you can double-click the corresponding branch/tag label. Alternatively, you can select the branch or tag to be checked out with the drop-down list on sections `Check out branch` and `Check out tag`. The currently checked out branch is highlighted with a bold font and enclosed in asterisks.

When adding a new branch, the naming rules apply as described in section <<commit-ids>>. If you happen to use a whitespace character in a branch or tag name, then this will automatically be replaced with an underscore.

=== Resetting a Branch

You can reset the currently checked out branch. This operation will move the branch label to the specified target commit. To do so, enter the target commit id, to which the branch should be reset, into the text field on the `Reset branch` section on the `Refs` tab and click the icon button on the text field. This might result in a number of commits getting lost in the reflog.

In the current version, you can only move around branch labels with this operation. It is not yet possible to visualize the difference between hard, soft, and mixed resets.

== Merging and Rebasing

On the `Merge/Rebase` tab you can merge two branches (_octopus merges_ are not supported) or rebase one branch onto another.

=== Merge

To merge two branches with each other, you select the target branch to be merged with the drop-down list on section `Merge branch`. If a fast-forward merge is possible, it will automatically be performed, unless you select the checkbox `No fast-forward merge`. If this checkbox is selected, an explicit merge commit is created.

The commit id for a merge commit consists of the concatenated ids of the merge commit's two parent commits. For example, if the two branches `foo` and `bar` with the respective most recent commit ids `f6` and `b3` are merged, the merge commit's id will become `f6b3`.

==== Merge Conflicts

A merge conflicts when, counted from the merge base, both branches contain at least one commit marked as `Conflicting change` (see <<Conflicting Changes>>). A fast-forward merge never conflicts, and neither does a merge where only one side or neither side has a marked commit. To set up a conflict, mark one commit on each branch and merge them. Instead of creating the merge commit, the repo stops: its header shows the red badge `MERGING - CONFLICT`, the marked commits of both sides are circled in red, and the `Merge/Rebase` tab shows a message with the buttons `Continue` and `Abort`. Click `Continue` to create the (unmarked) merge commit as usual, or `Abort` to leave the graph exactly as it was before the merge.

While the conflict is pending, every other operation on that repo (commits, branches, tags, checkout, merge, rebase, reset, cherry-pick, garbage collection, clear, push, fetch, pull, clone) and `Share` are refused with `Resolve the conflict first: Continue or Abort`. Other repos can be activated and used normally; the buttons are shown only while the active repo has a pending conflict.

=== Rebase

To rebase the currently checked out branch onto another branch, you select the target branch with the drop-down list on section `Rebase branch onto`. This will create new commits on the target branch for each commit on the rebased branch. The old commits will be lost in the reflog. The new commits are given the color and ids of the rebased commits with an additional asterisk appended. 

A rebase conflicts when the target side has at least one commit marked as `Conflicting change` since the merge base (see <<Conflicting Changes>>) and a marked commit of the rebased branch is about to be replayed. The rebase then stops in the middle, as Git does: HEAD is detached on the last replayed copy (or on the target when the first commit conflicts), the branch label stays on the original tip, the commits still to replay stay visible as the original commits, the conflicting commits are circled in red, and the repo header shows `REBASING n/m - CONFLICT` (n = the commit being replayed, m = the total). The copies reachable from HEAD are not shown as lost commits. Click `Continue` to replay the stopped commit (its copy keeps the marker) and go on until the next conflict or the end, where the branch moves to the new tip and HEAD is attached again; every marked commit of the rebased branch stops once. Click `Abort` to restore branch and HEAD as they were before the rebase; the replayed copies become lost commits (and the swimlane shift made at the start of the rebase remains). The same applies when the rebase is started from a detached HEAD: at the end HEAD stays detached on the new tip, and `Abort` puts HEAD back on the commit it started from. If only one side has a marked commit, the rebase runs through without stopping. While the conflict is pending, other operations are refused as described in <<Merge Conflicts>>.

== Remote Repositories [[remote-repositories]]

The `Remote` tab lets you demonstrate working with a remote repository. A remote is simply another repository on the canvas; no network is involved. The remote repository's HEAD label is greyed out, because a real remote is a bare repository without a working tree; you can still commit or check out in it to simulate a colleague's push.

=== Clone

Select a repository and click `Clone repository`. A new repository region appears (the canvas holds at most three repositories). It contains copies of all commits and tags (lost commits are not copied) with the same ids, colors and layout, plus one checked-out local branch. For each branch of the source, a _remote-tracking branch_ labeled `origin/<name>` is shown as a dashed, unfilled label in dark red. The checked-out branch tracks its `origin/<name>` as its _upstream_. The source repository becomes the clone's `origin`. The clone is placed directly below its origin; cloning the same origin a second time moves the first clone to the left and puts the new clone to the right, so origin and clones form a triangle. A clone of a clone appears below that clone.

Repository regions grow upward and to the right as you add commits and branches. If a region would come too close to another one, the app automatically moves the lower or right-hand repository further down or to the right so that regions never overlap. Regions never move back, and the new positions are part of the Share URL.

Remote-tracking branches can be checked out like in Git. Double-clicking an `origin/<name>` label (or selecting `origin/<name>` in the `Check out branch` list, or typing it into the `Check out` input) detaches `HEAD` on that commit; no branch is created. Checking out a plain `<name>` that has no local branch but an `origin/<name>` (the `Check out branch` list offers such names) creates the local branch `<name>` at the same commit, with `origin/<name>` as its upstream, and attaches `HEAD` to it. An existing local branch of that name is always preferred. If the new branch name's first letter is already used by another branch, the checkout is refused with a message.

The remote relationship is visible on the canvas. As soon as a repository has a clone, its region gets a dashed border, a light tinted background and a `REMOTE` badge next to its name (dashed means remote, like the remote-tracking labels). Each clone shows `origin -> <remote name>` in its header, and a line labelled `origin` connects the clone to its origin. A clone of a clone shows both cues.

=== Remote Tab Status

For the active repository the tab shows its remote (`origin: <repository name>`, or `(not available)` if the remote repository was cleared), the upstream of the checked-out branch, the ahead/behind counts relative to that upstream, and a message area with the result of the last operation.

=== Push

`Push` transfers the commits of the checked-out branch that the remote lacks and moves the branch on the remote to the local tip. A branch without an upstream gets `origin/<same name>` as upstream on its first push. If the remote branch has commits that the local branch does not contain, the push is rejected with `rejected: non-fast-forward - fetch first`, and the remote region flashes red briefly. Fetch and integrate the remote changes first. If the remote already has everything, the message is `Everything up-to-date`. If the remote repository is not available, the message is `remote not available`.

=== Fetch

`Fetch` copies all commits from the remote that are missing locally and creates, moves, or removes the `origin/<name>` labels to match the remote's branches. Local branches and HEAD are never moved. If nothing changed, the message is `Already up to date`.

=== Pull

`Pull` is a fetch followed by merging the upstream `origin/<name>` into the checked-out branch. The fetch summary (e.g. `Fetched: ...`) is shown in front of the pull result. If the branch already contains the upstream, nothing is merged and the message is `Already up to date`. If a fast-forward is possible it is performed (message `Fast-forward`); otherwise a merge commit is created (`Merge made`). Pull is not possible in detached HEAD state or for a branch without upstream. If the local branch and `origin/<name>` both contain a marked commit since their merge base, the pull stops after the fetch with `MERGING - CONFLICT` exactly like a merge (see <<Merge Conflicts>>); use `Continue` or `Abort` on the `Merge/Rebase` tab. A typical demo: two clones each commit a marked change, the second push is rejected, and the pull then conflicts.

=== Pull With Rebase

If the `rebase` checkbox is selected, `Pull` rebases the checked-out branch onto its upstream instead of merging, so no merge commit is created (message `Rebased`, or `Fast-forward` if the branch had no own commits). The rebased commits get the usual asterisk suffix. If the branch and `origin/<name>` both contain a marked commit since their merge base, the pull stops after the fetch with `REBASING n/m - CONFLICT` exactly like a rebase (see <<Rebase>>); use `Continue` or `Abort`.
